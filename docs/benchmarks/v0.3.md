# v0.3 benchmarks

Recorded 2026-10-07 for work package M6 (roadmap v0.3, design §22,
D251–D253): what a request costs in Anetos, compared with the same
work written by hand with `net/http` and `database/sql`, and with chi,
Gin and Echo; what each part of an app's page costs; and the
optimizations M6 made.

## Method

- **Code:** [`bench/`](../../bench). Every request is served in-process
  (`ServeHTTP` with `httptest`), so the numbers are the framework's cost
  without the network. Each iteration also builds the `httptest`
  request and recorder (about 2.5µs, 5 KiB and 9 allocations, plus the
  recorder's writes), the same in every variant: compare differences,
  not ratios.
- **Variants:**
  - **Mux:** `http.ServeMux` and hand-written code doing the same work
    (parse the path value, decode and check the JSON, query and scan,
    encode JSON). The reference.
  - **Router:** a bare `web.Router`; a typed handler (`web.H`) for JSON
    and the DB read, a plain one for hello.
  - **Server:** the router of `web.NewServer`, with its default
    middleware: recover, request IDs, real IP, security headers, body
    limit and request timeout (access log off; the units and locale
    steps do nothing without their setup). What an API serves.
  - **Chi, Gin, Echo:** the same hello and JSON work in chi v5.3
    (handlers decoding by hand, like Mux), Gin v1.12 and Echo v4.16
    (their binding, with go-playground/validator for the same rules),
    bare, without middleware: compare with **Router**. Fiber isn't
    measured: it runs on fasthttp, not `net/http`, so it can't serve the
    same in-process requests.
- **Workloads:**
  - **Hello:** `GET /` answering a short text.
  - **JSON:** `POST /authors/{id}/posts` binding a path value and a
    JSON body, validating two fields (`required|max:200`, `required`)
    and answering 201 with JSON.
  - **DB read:** `GET /posts/{id}` reading one row by primary key from
    SQLite in memory and answering JSON; **Query** is a query alone,
    without HTTP: one row (`QueryRowScan`, `QueryFind`), or 20 rows of a
    list (`QueryListScan`, `QueryList`).
  - **Page:** `GET /posts` for a signed-in user, as an app made with
    `anetos new` and `make:auth` serves it: the server's middleware with
    the access log on (JSON, to `io.Discard`), the request's language,
    the session in an encrypted cookie, CSRF, the signed-in user loaded
    from the database, 20 rows, and HTML written as templ writes it. Its
    parts, measured on a hello route with more and more of the stack:
    **Server** (middleware and locale), **Session**, **CSRF**,
    **SignedIn**; **Full** is the page. It has no hand-written
    equivalent: one would be most of a framework.
  - **Middleware:** a bare router with one middleware, on the hello
    route: compare with **HelloRouter**.
- **Machine:** cloud container, 2 vCPU Intel Xeon @ 2.10GHz,
  linux/amd64, Go 1.27.1. `go test -bench . -benchmem -count 8`,
  summarized with `benchstat` (medians; the run-to-run spread is ±2–6%).
  Times on another machine differ; the differences between variants
  and the allocations carry over.
- **Code version:** M6's code, before two small fixes from its review
  (a sub-request's own request state; the key cache's two
  generations), which leave every allocation count unchanged
  (`make bench-check`).

## M6's optimizations

The same benchmarks before and after M6's changes (design D252), built
and run in turns on one machine (`scripts/bench-compare.sh`, six rounds
of 0.5s): [before](v0.3-m6-before.txt), [after](v0.3-m6-after.txt).

| Benchmark | Before | After | Change |
|---|---|---|---|
| HelloServer | 8.01µs, 48 allocs | 6.73µs, 41 allocs | −16% |
| JSONServer | 11.81µs, 65 allocs | 10.74µs, 58 allocs | −9% |
| DBReadServer | 34.58µs, 138 allocs | 33.05µs, 126 allocs | −4% |
| QueryList | 78.07µs, 451 allocs | 73.00µs, 332 allocs | −6%, −26% allocs |
| Page/Session | 32.22µs, 140 allocs | 22.79µs, 99 allocs | −29% |
| Page/SignedIn | 65.56µs, 236 allocs | 55.63µs, 190 allocs | −15% |
| Page/Full | 186.62µs, 725 allocs | 162.16µs, 559 allocs | −13%, −23% allocs |

- **One context value per request.** `RequestIDs`, `RealIP` and the
  locale middleware each added a context value and a copy of the
  request; in a router they now keep their results in its request
  state, and the locale middleware no longer adds the translator the
  server's base context already has.
- **Cheaper request IDs.** They come from `math/rand/v2` instead of
  `crypto/rand` and are encoded straight into lowercase: the same 16
  characters, unique but not secret (they never were). Most of
  `RequestIDs`' gain is the context value it no longer adds.
- **Sessions aren't encoded to be compared.** A session encoded its
  payload twice per request (on load and on save) to see whether it
  changed; it now notes changes as its methods make them.
- **Derived keys are cached.** Each encrypted message has a key derived
  from `APP_KEY` and its salt (HKDF): most of the cost of opening a
  session cookie, which a browser sends unchanged on each request.
  `encryption` keeps those of the last 1024 to 2048 messages, by key
  and salt, once a message opened with them. The benchmark sends one
  cookie, the cache's best case; with more active sessions than the
  cache holds, it helps less.
- **Row scanning reuses its scanners.** The scanners of time and JSON
  columns were allocated for each column of each row, and times were
  boxed; a list of 20 rows now allocates no more than the hand-written
  loop.

## Analysis

- **Routing and typed handlers stay cheap:** 0.6µs over `net/http` for
  hello, 1.3µs with JSON binding and validation, in line with chi, Gin
  and Echo, which are within a microsecond of each other and of Anetos
  on this work. None of these differences matter next to a database
  query.
- **The server's default middleware costs about 3µs.** The timeout's
  context is the dearest part (1.1µs), and with a database it costs
  more: `database/sql` watches a cancelable context with a goroutine per
  query, which is most of the DB read's 7µs between Router and Server.
  It is worth it: a request that hangs is cut off.
- **The access log costs 2.4µs a request** in JSON, the price of
  formatting a line; most apps keep it.
- **A signed-in page is dominated by the database.** Of the page's
  161µs, the two queries take about 90µs alone (the user about 18µs,
  the list about 72µs) and more under the request's timeout context;
  the session cookie 11µs; writing the HTML of 20 rows 3.6µs.
  Against PostgreSQL or MySQL over a network, each query also waits a
  round trip (100µs or more), so the framework's share is smaller
  still. Caching what a page reads helps far more than anything in the
  framework could.
- **`db.Find` costs about 5µs over a hand-written query** (building the
  SQL, the scan plan's lookup, the scanners); a list of 20 rows costs
  the same few microseconds and no more allocations than the
  hand-written loop. Caching the SQL of simple queries is the next
  candidate.
- **SQLite's driver parses each time twice:** modernc.org/sqlite tries
  `time.Time.String`'s format before the one it writes, so each time
  value costs a failed parse (about a fifth of the page's allocations). It
  affects hand-written code the same way; it is a candidate for an
  upstream fix.

## The gate

From v0.3, every change is held to these numbers (design §22, D251):

- **Allocation budgets** (`make bench-check`, in `make check` and every
  CI run): the allocations beyond the hand-written work for the router,
  the server, the JSON handler and `db.Find`, exactly; and the page's
  parts in all, with headroom for the standard library's own changes
  between Go releases (growth within it is left to the next check).
- **Pull requests** are compared with their base branch on the same
  runner (`make bench-compare BASE=main` does it locally): more
  allocations, or a median more than 20% slower with every sample
  slower, fail the check (one chance in 252 per benchmark that noise
  alone orders the samples so; the 20% makes it rarer). The label
  `benchmark-ok` accepts a regression; the check runs again when a
  label changes.
