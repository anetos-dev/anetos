# v0.1 baseline

Recorded 2026-09-30 for the v0.1 exit criterion "a baseline benchmark
against plain `net/http`" (roadmap v0.1, design §22).

## Method

- **Code:** [`bench/bench_test.go`](../../bench/bench_test.go). Every
  request is served in-process (`ServeHTTP` with `httptest`), so the
  numbers are the framework's cost without the network. Each iteration also
  builds a `httptest` request and recorder (about 2.5µs, 5 KiB and 9
  allocations, plus the recorder's writes), the same in every variant.
- **Variants:**
  - **Mux:** the standard library's `http.ServeMux` with hand-written code
    doing the same work (parse the path value, decode and check the JSON,
    scan the row, encode JSON).
  - **Router:** a bare `web.Router` with a typed handler (`web.H`).
  - **Server:** the router of `web.NewServer`, with its default middleware:
    recover, request IDs, real IP, security headers, body limit and request
    timeout (access log off). This is what an app runs.
- **Workloads:**
  - **Hello:** `GET /` answering a short text.
  - **JSON:** `POST /authors/{id}/posts` binding a path value and a JSON
    body, validating two fields (`required|max:200`, `required`) and
    answering 201 with JSON.
  - **DB read:** `GET /posts/{id}` reading one row by primary key from SQLite
    in memory (`drivers/sqlite`, one connection) and answering JSON.
    `QueryRowScan` and `QueryFind` are the query alone, without HTTP.
- **Machine:** cloud container, 2 vCPU Intel Xeon @ 2.10GHz, linux/amd64,
  Go 1.27.1. `go test -bench . -benchmem -count 8`, summarized with
  `benchstat` (median ± 95% confidence interval).

## Results

| Workload | Mux | Router | Server | Router vs Mux | Server vs Mux |
|---|---|---|---|---|---|
| Hello | 3.48µs, 18 allocs | 3.80µs, 24 allocs | 6.43µs, 47 allocs | +9% (noise: ±17%) | +84%, +2.9µs |
| JSON | 5.67µs, 32 allocs | 6.94µs, 41 allocs | 10.14µs, 64 allocs | +22%, +1.3µs | +79%, +4.5µs |
| DB read | 19.30µs, 68 allocs | 25.12µs, 103 allocs | 30.48µs, 137 allocs | +30%, +5.8µs | +58%, +11.2µs |

| Query alone | Time | Memory |
|---|---|---|
| `database/sql` `QueryRowContext(…).Scan(…)` | 13.01µs | 1.7 KiB, 47 allocs |
| `db.Find[Post](ctx, id)` | 18.16µs | 3.2 KiB, 74 allocs |

## Analysis

- **The router and typed handlers are cheap.** Routing, `web.Ctx`, binding
  and validation cost about 0.3–1.3µs over hand-written `net/http` code
  that does the same checks.
- **The default middleware costs about 3µs per request** (23 allocations):
  a request ID, security headers, a body-limit wrapper and a timeout
  context. Most apps want all of them; per-middleware costs aren't
  measured yet.
- **The timeout context makes database reads dearer.** A cancelable request
  context makes `database/sql` start a goroutine per query to watch it. The
  Server DB read pays about 5µs more than the Router one, versus 3µs for
  the other workloads.
- **`db.Find` costs about 5µs over a hand-written query and scan**
  (+27 allocations): building the SQL for each query, the row scanner and
  the time-column decoding. While recording this baseline, caching each
  model's quoted column list per dialect took `db.Find` from 101 to 74
  allocations. Next candidates: caching the whole SQL of simple queries
  (`Find`, `First` by key) and pooling scanners.
- **In context:** the largest overhead measured, 11µs on the DB read, is
  below one network round trip inside a data centre, and SQLite in memory
  is the fastest database a request can hit. With PostgreSQL or MySQL over
  a network, the framework's share shrinks further.

Targets follow from these numbers when the regression gate is set up
(design §22, roadmap M6).
